# Migrating from LLDAP to KLLDAP 0.7

KLLDAP 0.7 can take over a database created by stock upstream
[LLDAP](https://github.com/lldap/lldap) **0.6.x** (database schema **11 or
older**). Users, groups, memberships, custom attributes and their values survive.
Passwords do not: the OPAQUE library changed between LLDAP 0.6.x and KLLDAP, so
every user sets a new password after the move — which is also when a Kerberos
principal is created for users with `kerberosSync` on. This path is exercised
in CI against a genuine lldap 0.6.3 database (`server/tests/migration_compat.rs`).

If your LLDAP is older than 0.6, upgrade it within LLDAP first and boot it once
so its own migrations run. Databases from unreleased upstream versions with a
schema newer than 11 are not supported.

## The short version

1. Stop LLDAP and **back up the database**.
2. Point KLLDAP at the *same* database (`database_url`) with a **fresh key**:
   set your own `key_seed`, or let KLLDAP create a `key_file` under `/data`. Do
   not reuse LLDAP's `server_key` or `key_seed`: the passwords they protected
   cannot be verified anymore, and an old key file usually fails to parse.
3. Start KLLDAP once with `LLDAP_FORCE_UPDATE_PRIVATE_KEY=true`,
   `LLDAP_FORCE_LDAP_USER_PASS_RESET=true` and `LLDAP_LDAP_USER_PASS=<admin
   password>`. It applies schema v12 and v13, records the new key, resets the
   admin password, and exits with "Restart the server without
   --force-update-private-key …" — that exit is expected, and the container
   stops with it.
4. Remove the two `FORCE` variables and start KLLDAP normally.
5. Every user sets a new password: the web UI's reset link (needs SMTP), an
   admin from the web UI or `setUserPassword`, or `lldap_set_password`.

## What the migration does

On that first boot KLLDAP appends its own schema versions (v12, v13) to the
upstream chain. Nothing upstream is destroyed; the steps are idempotent:

- KLLDAP's organizational-unit and Kerberos columns and defaults are added.
- Upstream's `JpegPhoto` attribute type becomes KLLDAP's `Avatar` — including
  custom attributes you defined with that type. Over LDAP and GraphQL the name
  `JPEG_PHOTO` remains accepted as an alias.
- Attribute values are re-encoded from upstream's binary encoding into
  KLLDAP's canonical one (strings stay strings, dates become epoch seconds,
  photos raw JPEG bytes — byte-identical). Values the converter does not
  recognize are logged and left untouched, never destroyed.
- Leftover duplicate schema rows from old upstream versions (`first_name` vs
  `firstname`) are folded into the canonical spelling.

Custom attribute schemas and their values persist. If you created a custom
attribute whose name is one of KLLDAP's LDAP aliases for a built-in
(`givenName`, `sn`, `mail`, `cn`, `uid`, …), its *values* are folded into the
built-in attribute during migration, though the schema entry itself survives.

## Databases

SQLite and PostgreSQL are gated in CI. MySQL/MariaDB is best-effort: the
migration is written to work there, but it is not part of the test gate — take
a dump first and file an issue if something misbehaves.

## Troubleshooting

- **"The private key has changed" / "The contents of the private key file …
  have changed"** — the database remembers a different key. That is expected on
  the first boot after the move: run it once with the two `FORCE` variables
  (step 3), then without them.
- **"while parsing the contents of the `server_key` file"** — an LLDAP key file
  was reused. Use a fresh key (step 2).
- **A user cannot log in after migration** — passwords do not carry over; set a
  new one (step 5).

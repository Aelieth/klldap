# Migrating from LLDAP to KLLDAP 0.7

KLLDAP 0.7 can take over a database created by stock upstream
[LLDAP](https://github.com/lldap/lldap) **0.6.x** (database schema **11 or
older**) with data and passwords intact. This path is exercised end-to-end in
CI against a genuine lldap 0.6.3 database and key
(`server/tests/migration_compat.rs`).

If your LLDAP is older than 0.6, upgrade it within LLDAP first and boot it once
so its own migrations run. Databases from unreleased upstream versions with a
schema newer than 11 are not supported.

## The short version

1. Stop LLDAP.
2. **Back up the database and the `server_key` file.**
3. Point KLLDAP at the *same* database (`database_url`) and the *same*
   `server_key` file (`key_file`).
4. Start KLLDAP. The schema migrates to v13 automatically.
5. Users keep their passwords: each account upgrades transparently the first
   time it authenticates through an **LDAP bind** or **`POST
   /auth/simple/login`** (which is what almost every integrated app does).

## What the migration does

On first boot KLLDAP appends its own schema versions (v12, v13) to the upstream
chain. Nothing upstream is destroyed; the steps are idempotent and safe to
re-run:

- KLLDAP's organizational-unit and Kerberos columns and defaults are added.
- Upstream's `JpegPhoto` attribute type becomes KLLDAP's `Avatar` — including
  custom attributes you defined with that type. Over LDAP and GraphQL the name
  `JPEG_PHOTO` remains accepted forever as an alias.
- Attribute values are re-encoded from upstream's binary encoding into
  KLLDAP's canonical one (strings stay strings, dates become epoch seconds,
  photos raw JPEG bytes — byte-identical). Values the converter does not
  recognize are logged and left untouched, never destroyed.
- Leftover duplicate schema rows from old upstream versions (`first_name` vs
  `firstname`) are folded into the canonical spelling.

Custom attribute schemas and their values are yours and persist. One caveat: if
you created a custom attribute whose name is one of KLLDAP's LDAP aliases for a
built-in (`givenName`, `sn`, `mail`, `cn`, `uid`, …), its *values* are folded
into the built-in attribute during migration, though the schema entry itself
survives.

## Passwords

LLDAP never stores passwords, only OPAQUE registration records, and the OPAQUE
library versions differ between LLDAP 0.6.x and KLLDAP. KLLDAP therefore keeps
a verifier for the legacy format: when a user authenticates via LDAP bind or
`/auth/simple/login`, the password is checked against the current format first,
then the legacy one; on a legacy success the record is transparently
re-registered in the current format. No user action, no flag, no deadline —
a record upgrades whenever its owner next logs in.

The one exception is the **web UI login**, which runs OPAQUE in the browser
and cannot verify a legacy record. A user who only ever uses the web UI should
either log in once through anything that does an LDAP bind or simple login, or
use the password reset flow.

The `server_key` file is accepted in both formats; the private key, and the
private-key fingerprint stored in the database, carry over unchanged.

## If you used `key_seed` instead of a key file

There is no continuity for seeds: the derivation from seed to key changed
between the OPAQUE libraries, so the same seed produces a *different* key in
KLLDAP, and no supported way exists to re-create the old key from the seed.

Migrate the data anyway, but plan for password resets:

1. Remove `key_seed` from the configuration.
2. Start KLLDAP once with `--force-update-private-key=true` — it generates a
   fresh `server_key` file (keep it!).
3. Every user resets their password (or you set them via
   the admin UI / `lldap_set_password`).

## Databases

SQLite is gated in CI. PostgreSQL is supported (the same migrations) and will
be gated in a later pass. MySQL/MariaDB is best-effort: the migration is
written to work there, but it is not part of the test gate — take a dump first
and file an issue if something misbehaves.

## Troubleshooting

- **"while parsing the contents of the `server_key` file"** — the file is not
  a valid key in either format. Usually a truncated copy or the wrong file;
  restore it from the LLDAP host (it is exactly 128 bytes).
- **"The contents of the private key file … have changed" / "The private key
  has changed"** — the key in the file does not match the fingerprint stored
  in the database: this database's passwords were registered under a different
  key. Find the original `server_key` that belonged to this database. If it is
  truly gone, restart once with `--force-update-private-key=true
  --force-ldap-user-pass-reset=true` and have all users reset their passwords.
- **A user cannot log in after migration** — if they only ever used the web
  UI, see the web UI note above. Otherwise verify the same `server_key` file
  made the move.
